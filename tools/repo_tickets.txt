Title: Implement JSON / structured output (-Json, -OutputFile, -PassThru)
Issue: #1
Status: closed
Labels: enhancement
Body:
The result-output features documented in `docs/json-output.md` are declared but
not implemented in `source/delphi-format.ps1`. The three parameters exist only
as no-ops -- each carries a `PSReviewUnusedParameter` `SuppressMessageAttribute`
because PSScriptAnalyzer flags them as unused:

- `-Json`: currently only sets `$script:SuppressOutput`, silencing the
  `Write-Detail`/`Write-Summary`/`Write-Section` helpers. It does NOT emit the
  documented `{ Engine, Root, Mode, FilesScanned, FilesFormatted, ..., Items[] }`
  object. Net effect today: `-Json` on a format/check/whatif run emits nothing.
- `-OutputFile <path>`: declared (`delphi-format.ps1:118`) but never written. No
  structured result file is produced for CI integration.
- `-PassThru`: declared but never returns objects to the pipeline.

Correctly implemented and NOT in scope here: `-Version -Format json` and
`-ShowConfig -Json`, which already emit valid JSON.

Design note / blocker to resolve as part of this work: the documented per-file
`Items[]` array (with per-file `Status` and `DurationMs`) and the
`FilesFormatted`/`FilesUnchanged`/`FilesFailed` counts cannot be produced by the
current engine invocation. `Invoke-FormatEngine` runs a single batch
`Start-Process` over all files and returns one overall exit code, so there is no
per-file result tracking. Implementation must add per-file result capture (or
document a reduced shape) rather than emit fields the engine cannot populate.

Downstream dependency: `delphi-powershell-ci`'s `Invoke-DelphiFormat` wrapper is
documented to parse the `-OutputFile` result (docs/json-output.md), so this
contract must land before that integration can be completed.

Acceptance criteria:
- [ ] `-Json` emits the object documented in `docs/json-output.md` for Execute,
      WhatIf, and Check modes, with all other stdout suppressed.
- [ ] Per-file `Items[]` and the summary counts are backed by real per-file
      result tracking (engine invocation refactored as needed), OR the doc and
      output are reconciled to a shape the tool can actually produce.
- [ ] `-OutputFile <path>` writes the structured CI result JSON documented in
      docs/json-output.md.
- [ ] `-PassThru` returns result objects to the pipeline.
- [ ] The `PSReviewUnusedParameter` suppressions for `Json`/`PassThru`/`OutputFile`
      are removed (params are now genuinely consumed) and PSScriptAnalyzer stays
      clean.
- [ ] `docs/json-output.md` matches the shipped behavior exactly.
- [ ] Pester coverage for `-Json`, `-OutputFile`, and `-PassThru` across modes.

Title: Validate engine-specific config keys against the selected engine
Issue: #3
Labels: enhancement
Body:
The original plan (`delphi-format.md` lines 485-487) calls for runtime
validation of engine-specific config keys: "if a key only applies to one
engine, emit a warning or error when used with the wrong engine." This is
currently unimplemented -- keys meant for one engine are silently ignored when
another engine is selected, which hides configuration mistakes.

The most concrete case is radFormatter-only keys (e.g. the `profile` key added
by the "expose -Profile" ticket) being present while `engine` resolves to
`formatter`. Today that produces no diagnostic; the key is simply dropped.

Implementation notes:
- After the effective config is resolved and the effective engine is known,
  check for keys that do not apply to that engine.
- Maintain a small map of engine -> set of keys that are exclusive to it (and
  the shared keys that apply to both). At minimum, radFormatter-exclusive:
  `profile` (once added). formatter.exe has no exclusive orchestration keys
  today, but the mechanism should be table-driven so new keys slot in.
- Decide and document the severity: recommend a non-fatal `Write-Warning`
  (e.g. "Config key 'profile' applies only to the 'radFormatter' engine and is
  ignored for engine 'formatter'.") rather than a hard failure, so a shared
  config that targets multiple engines across repos does not break. Confirm the
  warning is suppressed under `-Json` (routed so it never corrupts JSON stdout).
- Ensure the validation runs after CLI overrides are applied, so it reflects the
  truly effective engine, not just the config-file engine.

Acceptance criteria:
- [ ] A radFormatter-only key present with `engine = formatter` produces a clear
      warning naming the key and the engine, and the run still proceeds.
- [ ] The check is table-driven so additional engine-exclusive keys are easy to
      register.
- [ ] The warning does not appear on stdout when `-Json` is set (no JSON
      corruption).
- [ ] `docs/configuration.md` documents which keys are engine-specific and the
      warning behavior.
- [ ] Pester coverage for the wrong-engine-key warning path.

Title: Expose radFormatter -profile as a first-class parameter and config key
Issue: #4
Status: closed
Labels: enhancement
Body:
radFormatter supports a `-profile <name>` flag selecting a base config profile
(`Default`, `FormatterExe`, `Embarcadero`, `NoOp`) -- see `delphi-format.md`
lines 748-752 / 808. delphi-format does not currently expose it, so users cannot
select a radFormatter base profile through this tool.

Add a `-Profile` parameter and a matching `profile` orchestration config key,
and pass the value through to radFormatter via `-profile` in
`Invoke-FormatEngine`.

Explicitly OUT OF SCOPE (do not add): radFormatter's `-writeDefaultConfig` and
`-trace`. `-writeDefaultConfig` is a config-bootstrapping/emit-and-exit mode
that does not fit this tool's format/check orchestration surface, and `-trace`
is a debugging aid. This ticket covers `-profile` only.

Implementation notes:
- Add a `Profile` parameter to the Format parameter set. Use
  `[ValidateSet('Default','FormatterExe','Embarcadero','NoOp')]`.
- Add `profile` to the supported config keys and the CLI-override pass in the
  main block (CLI wins over config, same pattern as `engine` / `encoding`).
- In `Invoke-FormatEngine`, when `$EngineName -eq 'radFormatter'` and a profile
  is set, add `-profile <value>` to the engine argument list. Also apply it in
  `Invoke-FormatEngine`'s radFormatter check path so `-Check` respects the
  profile.
- `profile` is radFormatter-only. Coordinate with the "engine-specific config
  validation" ticket: selecting `-Profile` with `engine = formatter` should
  warn (or, if that ticket is not yet done, at least be ignored cleanly for
  formatter.exe, never passed to it).
- Update `docs/configuration.md` (new key) and README (new flag), and note the
  profile in `-ShowConfig` output.

Acceptance criteria:
- [ ] `-Profile <name>` and the `profile` config key are accepted and resolved
      through the normal config/CLI precedence.
- [ ] With `engine = radFormatter`, the resolved profile is passed as
      `-profile <name>` in both format and check invocations.
- [ ] `-Profile` is never passed to formatter.exe; using it with
      `engine = formatter` does not error the run.
- [ ] `-writeDefaultConfig` and `-trace` are NOT added.
- [ ] `docs/configuration.md` and `README.md` document the new parameter/key.
- [ ] Pester coverage: profile forwarded to radFormatter, and not to formatter.

Title: Fix Merge-FormatConfig dropping earlier array values when accumulated array has one element
Issue: #5
Status: closed
Labels: bug
Body:
`Merge-FormatConfig` (`source/delphi-format.ps1`) read the accumulated array
from the in-progress merged object via `Get-ConfigValue $merged $key` and gated
the append/dedupe branch on `$existing -is [System.Array]`. PowerShell unrolls a
single-element array to a scalar when it is returned from a function, so when the
accumulated `excludeDirectoryPattern` / `includeFilePattern` had exactly ONE
element, `Get-ConfigValue` returned that lone element as a string. The
`-is [System.Array]` check then failed and the else branch OVERWROTE the property
with the incoming layer's array, silently discarding the earlier value.

Impact: any config layering where an array key held a single value at the point a
higher-priority layer contributed to the same key lost the earlier entry --
contrary to the documented "arrays append + deduplicate across all sources"
behavior (`docs/configuration.md`). Concretely, a `$HOME` config excluding a
single directory plus a project config excluding a different single directory
resolved to only the project's value. Discovered while building the Config test
suite (#2); the searchParentFolders traversal tests reproduced it directly.

Fix (already applied alongside #2): read the existing value directly from the
merged object's property (`$merged.PSObject.Properties[$key]`) and normalize with
`@(...)` so the array type is preserved without unrolling; append + dedupe when
the property already exists, otherwise store the incoming array. The `.Count`
guard was dropped (an empty existing array simply appends nothing) to stay
compatible with `Set-StrictMode -Version Latest`, under which `.Count` on a
non-collection throws.

Acceptance criteria:
- [x] Merging two layers that each contribute a single distinct value to the same
      array key yields both values (append), not just the higher-priority one.
- [x] Case-insensitive de-duplication still holds across layers.
- [x] Behavior verified by the searchParentFolders traversal tests in
      `delphi-format.Config.Tests.ps1`.
- [x] `source/delphi-format.ps1` stays PSScriptAnalyzer-clean and PS 5.1 / strict-mode safe.
